# Переход проекта на GPU-компьютер

## Что уже подготовлено

- Рыночные признаки превращаются в фиксированные последовательности по 120 секунд с шагом 5 секунд.
- Датасет хранится в Parquet с ZSTD и переносится без SQLite/PyTorch.
- Валидация — только purged expanding walk-forward: будущие события никогда не попадают в обучение.
- Отдельно моделируются направление, utility действий HOLD/UP/DOWN, вероятность исполнения лимитной заявки и преимущество раннего выхода.
- Все кандидаты сначала проходят offline, затем shadow и paper. Автоматического допуска в LIVE нет.

## Модели

| Роль | Модели | Назначение |
|---|---|---|
| CPU baseline | CatBoost v14, LightGBM v1 | обязательная точка сравнения |
| Последовательная entry | TCN v1, GRU v1, Tiny Transformer v1 | режим рынка и динамика внутри 5 минут |
| Исполнение | fill_model v2 | `P(limit fill)` |
| Выход | exit_tcn v1 | HOLD/CLOSE и ожидаемая разница с удержанием |
| Контекст | Qwen2.5-7B-Instruct 4-bit | новости и объяснение; не единственный исполнитель сделки |

Полный машинно-читаемый каталог: `настройка_проекта/gpu_model_catalog.json`.

Текущий sequence dataset уже содержит direction и action-utility цели. Колонки `fill_up/fill_down`
зарезервированы, но намеренно не заполнены суррогатным результатом события: для `P(fill)` нужно накопить
фактический статус лимитных заявок. Это защищает модель от ложной разметки «выигрыш = исполнение».

## Перенос

1. Перенести проект целиком, кроме `.venv`, `.venv-gpu`, `__pycache__` и кэшей моделей.
2. Установить актуальный драйвер NVIDIA и Python 3.12 x64.
3. Проверить план без изменений системы:

   `py -3.12 подготовить_gpu_компьютер.py`

4. Создать отдельное окружение, установить CUDA-сборку PyTorch, зависимости, проверить GPU и собрать датасет:

   `py -3.12 подготовить_gpu_компьютер.py --execute --build-data`

CUDA Toolkit отдельно обычно не нужен: PyTorch wheel содержит runtime. Драйвер NVIDIA всё равно обязателен.

## Обучение

После подготовки сначала проверить каждый кандидат:

`\.venv-gpu\Scripts\python.exe -m polybot.models.gpu_training_orchestrator --model tcn`

Аналогично: `gru` и `tiny_transformer`. Финальный trainer будет запускать одинаковые фолды и сохранять веса, scaler, признаки, конфигурацию, seed, метрики и хэш датасета в новую версию артефакта.

## Критерии продвижения

- минимум 500 независимых OOS-событий;
- минимум 50 исполненных сделок каждого направления;
- положительный PnL не менее чем в 80% временных фолдов;
- нижняя граница bootstrap CI чистого PnL выше нуля;
- затем не менее 300 одинаковых shadow-событий;
- отсутствие деградации PnL, drawdown, Brier/ECE, задержки и баланса направлений.

Ни одна GPU-модель не заменяет текущую production/paper-модель автоматически. Переключение выполняется только после отчёта и ручного подтверждения.
# Контекст соседних событий

Новая схема датасета сравнивает три одинаковых walk-forward эксперимента: без истории, с 3 и с 12 полностью завершёнными пятиминутками. Текущий исход и события, завершившиеся после времени решения, никогда не используются. В production попадёт только вариант, который улучшает OOS PnL/калибровку и проходит promotion gate.

Перед копированием выполните:

```powershell
.\.venv\Scripts\python.exe .\подготовить_переход.py
.\.venv\Scripts\python.exe .\проверить_историю_событий.py
```

Финальный checksum базы создаётся только после остановки процессов, иначе часть данных остаётся в WAL:

```powershell
.\.venv\Scripts\python.exe .\запустить_проект.py stop
.\.venv\Scripts\python.exe .\подготовить_переход.py --checkpoint
```

Переносите `данные`, `модели`, `исходный_код`, `запуск`, `настройка_проекта`, корневые `.py` и конфигурацию. Не переносите `.venv`, `.venv-gpu`, кэши и журналы. `api_config.py` переносится отдельно безопасным способом. На новом компьютере используется Python 3.12 и команда:

```powershell
py -3.12 .\подготовить_gpu_компьютер.py --execute --build-data
```
